¿Qué componente de la arquitectura de Calico, llamado Typha, se vuelve especialmente relevante para la escalabilidad cuando un cluster crece hacia un número muy grande de nodos?

Typha actúa como una capa intermedia de caché y distribución de datos entre los servers de Kubernetes (donde vive el estado) y los agentes Felix de cada nodo, reduciendo la carga directa sobre el API server de Kubernetes que ocurriría si cada uno de miles de Felix consultara directamente ese API server por separado
Typha reemplaza por completo la necesidad de tener Felix corriendo en cada nodo del cluster, siendo un componente que sustituye esa función en vez de complementarla dentro de la arquitectura de Calico
Solo es relevante Typha si el cluster tiene exactamente un único nodo en total, sin ninguna necesidad real de reducir la carga sobre el API server con un número pequeño de agentes Felix consultando
El API server de Kubernetes nunca experimenta ninguna carga adicional real relacionada con el número de agentes Felix que consultan directamente su estado, independientemente de si Typha está presente o no en la arquitectura

Calico · Lección 28

¿Por qué miles de agentes Felix consultando directamente y de forma individual al API server de Kubernetes (sin Typha como intermediario) podría sobrecargar ese API server en un cluster muy grande?

Pista: cada uno de los agentes Felix consultaría directamente al mismo API server central compartido por todo el cluster; con miles de esos agentes haciendo consultas simultáneas sin ningún intermediario, la carga acumulada de peticiones podría exceder la capacidad real que ese único API server puede procesar eficientemente, mientras Typha actúa precisamente como una capa intermedia que consolida esas consultas, reduciendo significativamente la carga real que llega hasta el API server central.
